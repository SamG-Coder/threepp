# Ashore rendering-path audit — 2026-09-07

## Scope and evidence

Audited the readable local export `ashore-island-world-beautified/assets/IslandGame-BBHGt3vE.mjs`, the JavaScript compatibility slices, binary command handlers, and native OpenGL renderer. The export includes a bundled Three.js revision marker of 180. This is not a claim of complete Three.js compatibility.

An instrumented startup/exploration run recorded 64 command-buffer entry points and 311 distinct materials: 28 ShaderMaterial, 4 MeshBasicMaterial, 112 MeshStandardMaterial, 142 MeshDepthMaterial, 24 MeshPhysicalMaterial, and 1 RawShaderMaterial. 97 materials had alpha-to-coverage enabled. The trace recorded scalar, integer, vec2/3/4, mat3/4, float-array and vec3-array uniform commands. Instrumentation changes timing; its FPS is not a performance benchmark.

The trace includes four-sample half-float refraction and composer targets, including targets with depth textures. Startup allocations with samples=0 are followed by recreated samples=4 targets; an initial zero-sample allocation alone does not demonstrate dropped MSAA.

## Validation

`npm --prefix ThreeBrowserRuntime test` with `THREEBROWSER_RUN_GPU_TESTS=1`: 57 tests passed after the fixes above. Native stage rebuilt successfully. An additional fresh-process antialias=false check returned samples=0. The quality-persistence restart and live canopy capture were inspected. Increasing the render scale restores the application's selected quality but is not a performance optimization.

Only the previously authorized raw pointer-lock option was changed in the application export. No application shaders or logic were embedded into the runtime. This document records failures explicitly; it must not be presented as an all-paths pass or one-to-one visual certification.

## Material CPU optimization validation

Runtime material flushing now compares render-state fields directly, snapshots numeric uniform components instead of serializing them, avoids flattening already numeric typed arrays, caches uniform-block parsing by shader source, and iterates hook uniforms without allocating entry pairs. No application files or shader bodies were changed for this optimization.

The 57-test suite passes with GPU tests enabled. Added pixel checks verify vector, matrix and typed-array mutations between successive render passes; command checks verify unchanged values are omitted, shader source edits refresh uniform-block names, and block values remain live after layout caching. Runtime staging succeeded and a live scene capture was inspected.

A controlled seven-round CPU benchmark, alternating old/new order, measured a median 40.0 ms versus 3.0 ms for 320,000 unchanged built-in material checks. This isolates the render-state path; it is not a whole-frame gain. A 32,000-call shader-material workload measured approximately 148.2 versus 152.2 ms with simple constant components, and 152.7 versus 149.4 ms with fractional components. Numeric-uniform results are workload-dependent, not a universal speedup.

Live 20-second samples after 35-second warm-up at saved High quality were inconsistent: control 11.2 FPS, optimized 13.7 FPS, optimized repeat 8.1 FPS. The optimized capture includes the pause overlay; this is not a walking-performance measurement. These runs do not establish an end-to-end improvement. Native CPU/GPU waiting remains unseparated, frame overlap is unchanged, and the shader compilation failures listed above remain unresolved.

### Follow-up: object state and shader recompilation

Object flags and custom shadow-material handles now use direct field comparisons instead of rebuilding string signatures on every object visit. A controlled native renderer workload (500 empty meshes, 30 render calls per round, seven rounds alternating old/new order) measured median JS preparation of 8.23 ms before and 6.80 ms after. This is approximately 17% less preparation time in that workload, not a live application FPS claim. No draws, callbacks, simulation work or quality settings are skipped.

Rebuilding ShaderMaterial source or an onBeforeCompile hook now invalidates the uniform value cache. Previously an unchanged numeric value could be omitted even when a uniform changed from float to int, leaving native state with the old type. The GPU regression fails without invalidation and passes with it; both direct source edits and version-triggered hook rebuilds are covered. Command regressions verify changed object flags, unchanged-state suppression, and removal of shadow-material bindings. All 57 tests pass with GPU tests enabled.

### Follow-up: uniform command name encoding

Numeric-uniform and texture-uniform commands now share a reusable UTF-8 encoder and a bounded cache of encoded names (up to 1,024 entries, at most 256 encoded bytes per retained name). Values, texture handles and command ordering remain live; long names bypass retention and name churn clears the cache. No application-specific names are registered in runtime code.

An alternating seven-round command-preparation benchmark (100,000 commands, 128 repeating names, changing scalar values and texture handles) measured median 54.06 ms before versus 20.63 ms after, approximately 62% less time in that isolated path. Every round produced byte-for-byte identical 5,400,000-byte command buffers. This is not a whole-frame or FPS measurement. A new command regression checks UTF-8 names, changing values, texture binding order, encoding reuse and bounded retention under generated-name churn. All 58 tests pass with GPU tests enabled.
